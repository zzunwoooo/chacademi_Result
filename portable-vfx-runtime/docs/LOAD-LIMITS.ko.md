# 전체 마법 사전 로딩

설정 위치: `.minecraft/config/portablevfx/load-limits.properties`

```properties
max-packs=512
encoded-cache-mib=256
resident-rgba-mib=1024
prewarm-rgba-mib=1024
resident-systems=512
prewarm-systems=512
```

기본값은 검증된 97개 팩의 235개 시스템을 시작할 때 모두 준비하기 위한 1 GiB 예산입니다. 중복을 제거한 원본 텍스처의 RGBA 합계는 약 926.234 MiB이며, 모델 자료와 별도 렌더 타깃도 메모리를 사용합니다. CPU 디코딩 자료 약 1 GiB와 GPU 텍스처 약 1 GiB가 각각 필요합니다. JSON/압축 원본 약 97 MiB, Minecraft 자체, 후처리 타깃, UI 아이콘과 드라이버 비용은 별도입니다. 실제 PC의 RAM/VRAM에 여유가 있어야 합니다. HUD 아이콘은 이 전체 VFX 사전 로딩에 포함하지 않습니다.

시전 경로에서는 파일 읽기, PNG/GLB 디코딩, 새 효과 업로드나 비활성 효과 퇴출을 하지 않습니다. 준비되지 않은 효과는 그 시전을 중단하고 `not ready` 상태를 표시합니다. 용량 부족을 영구적인 잘못된 팩으로 기록하지 않습니다. 설정을 낮추어 일부만 준비했다면 전체 카탈로그를 사용하는 서버는 준비 목록을 비교해 사용을 차단할 수 있습니다. 메모리 부족을 해결하고 F3+T로 다시 로딩해야 하며, 시전 중 즉석 로딩으로 전환하지 않습니다.

클라이언트는 GPU 준비가 완료된 효과 ID 목록만 알립니다. 재로딩 시작·진행 중, 렌더러 오류, 실제 월드 깊이 준비가 남은 동안은 빈 목록입니다. 서버는 자신의 카탈로그에서 필요한 모든 단계 ID가 이 목록에 있는지 확인합니다. 일반 프로토콜 지원과 실제 카탈로그 준비 완료는 구분합니다.

`/이펙트도구 상태`에서 준비/상주/미준비/오류 수를 확인합니다. `설정오류`는 실제 JSON·파일·팩 등록 오류를 보여 줍니다. `resident-rgba-mib`는 64–1024, `prewarm-rgba-mib`는 16부터 상주 예산까지, 압축 캐시는 16–1024 MiB 범위입니다. 상주 예산만 낮추면 지정하지 않은 사전 준비 예산도 그 값 이하로 낮아집니다. 각 시스템의 별도 안전 제한도 적용됩니다.

GPU 준비는 작은 단계로 나누며 즉시 실행되는 executor에서도 재귀적으로 쌓이지 않습니다. 재로딩 세대가 바뀌면 오래된 준비 작업은 새 준비 목록을 게시하지 않습니다. 로딩 화면에 호환 깊이 타깃이 없으면 `world depth pending`이며, 첫 유효 월드 프레임에서 실제 깊이 포맷을 준비합니다. 준비되지 않은 타깃을 준비됐다고 보고하지 않습니다.

실제 전체 동시 상주 검증에서 235개 시스템과 729개 고유 텍스처를 모두 GPU에 올렸고, 보수적으로 계산한 상주 자료는 972,128,331바이트(약 927.09 MiB)였습니다. 235개 시스템의 첫 실행에서 추가 디코딩·텍스처 업로드·셰이더 링크·타깃 생성은 모두 0이었습니다. Java 최대 힙 3 GiB로 실행한 Mesa 소프트웨어 렌더러 프로세스의 최대 RSS는 약 4.03 GiB였습니다. 이는 순간적인 디코더·JVM·소프트웨어 GPU 비용을 포함하며, 실제 Minecraft/Iris 메모리·FPS 측정값은 아닙니다. 검증 기록은 `docs/catalog-prewarm-verification/`에 있습니다.
